# Staged Hermes recovery and repair

This is an **unselected, disposable-only** H2 feature checkpoint for issue 19, not a cutover or live-data recovery tool. The [frozen publication counterexamples](../compatibility/hermes-publication.md#deterministic-mixed-process-findings) still block qualification under ADR 0002. In particular, a recovery lease cannot revoke a peer's open SQLite handle, and ownership checks are not atomic with file replacement. No TypeScript, shared schema, lease protocol or package-selection change is made.

The [extracted API](../reference/hermes-recovery.md) is generated by `bash scripts/hermes-recovery-reference.sh`; `npm test` checks deterministic drift. Existing `Open`/`NewMemory` remain borrowed-handle primitives. Production session lifetime now uses `OpenDatabase` and `NewManagedMemory`, rather than introducing a second knowledge-store owner.

## Disposable embedding tutorial

Use only an absolute database path beneath a disposable synthetic root. Call `OpenDatabase(ctx, databasePath, RecoveryOptions{})`, then `NewManagedMemory(ctx, database, settings, resolvedPaths)`. The supplied knowledge and project roots must be absolute. End all synchronous memory operations before calling `Close`.

For a document saved before a crash or failed search update, call `memory.Reconcile(ctx, Scope{Target: "memory", Project: "synthetic-project"})`. Omit `Project` for global memory; `user` is global-only; `failure` reconciles the shared failure document and its attributed project scopes. This reads disk truth under the existing mutation lease and updates the search mirror without republishing the document. Missing documents are authoritative empty scopes; unreadable or invalid documents return an error, not an empty replacement.

Inspect both the returned error and `MutationResult.SearchReconciled`. Reconciliation failure retains the document, warning and repair advice; do not repeat an already durable add blindly. `Database.Status` exposes completion/degraded state and the last recovery result. Local errors and backup paths are not sanitized SDK notification payloads.

For database-only operations, use `database.Do(ctx, func(db *sql.DB) error { ... })`. The callback must be retry-safe, must close its rows and commit/roll back its transactions before returning, and must use context-aware SQL. Never retain the handle, reenter the database owner, or publish documents inside this callback. The owner retries the callback **once**, only for SQLite `CORRUPT`/`NOTADB` or its own integrity-check error. Busy, constraint, permission, cancellation and programming failures are not corruption. A failed recovery stops ordinary database admission until explicit `Recover` succeeds; no callback runs on a nil or knowingly degraded handle.

`CheckIntegrity` synchronously settles a scan when embedding needs an observation point. Normal open starts the same scan eagerly in an independently owned worker rather than blocking initialization on a full scan. It checks SQLite rows, foreign keys and both external-content FTS indexes. `Close` closes admission, cancels and joins that worker before closing SQLite, and returns degraded/cleanup failures rather than inventing clean shutdown. Callbacks that ignore cancellation can still delay draining; the owner never closes SQLite beneath them.

## Accepted recovery bounds and outcomes

Zero-valued options choose three failures in a five-minute window, three corrupt backup groups and a 30-second recovery/scan budget. `CircuitLimit`, `CircuitWindow` and `Timeout` can select positive bounds; negatives are rejected. `BackupRetention` is an optional nonnegative integer pointer, so an explicit zero disables successful-recovery backup retention. Lock wait/poll/stale pointers retain `RecoveryCoordination` defaults and override semantics, including zero wait; nonfinite timings are rejected. The owner copies pointer values instead of borrowing mutable options. These are embedding options, not newly accepted JSON settings.

The circuit retains the baseline `<database>.recovery-state.json` shape, `{ "failures": [millisecondTimestamp, ...] }`, with private atomic writes. Cutoff equality and future timestamps survive clock movement. Only missing state means no recorded failures; malformed, unreadable, symlinked or oversized state fails closed. Failed rebuild/restoration records a failure, successful recovery clears it, and an open circuit prevents another destructive attempt. Lock contention is not a failed rebuild.

Recovery outcomes distinguish:

- `reused`: the current file is healthy after joining recovery; reopen it without replacement.
- `rebuilt`: readable shared-table rows were streamed into the unchanged current schema. IDs, projects, categories, recall counts/dates, session-file metadata and arbitrary provenance metadata retain their values. Date text is copied without driver date reformatting.
- `recreated-empty`: no shared rows could be read. This is explicitly degraded salvage, not proof that the original store contained no data.

`RecoveredRows` counts copied rows, and `UnreadableTables`/`RecoveryResult.Degraded` expose incomplete salvage. A damaged table does not suppress readable rows already obtained from it or from other tables. Non-corruption copy failures abort instead of coercing values, silently skipping rows or pretending success. FTS and its version marker are rebuilt; `mdsync:v1:` fingerprints are deliberately omitted so document scopes can be repaired. Successful salvage can leave a structurally healthy database with incomplete historical data; `DatabaseStatus.Recovery.Degraded` continues to expose that fact even while new database work is admitted.

The old main/WAL/SHM set is moved into one `.corrupt-*` group, with token checks separately preceding filesystem operations. Permission bits are preserved on the replacement. On partial move or failed verification, restoration copies retained backups through private staging and no-clobber links; it never deletes a preexisting destination to force rollback. `RecoveryError` preserves the result and cause for failed initialization as well as explicit recovery. A failed candidate can remain in a separate `.corrupt-*-failed` main/WAL/SHM group for inspection. Backups remain available when restoration fails; ordinary work stays degraded.

Successful recovery prunes corrupt main/WAL/SHM groups to the configured count. Failed recovery also attempts bounded pruning, keeping the current original source group before failed candidates and older groups. Explicit zero retention preserves one source group after failure rather than destroying the only rollback material. Failed candidates participate in the same cap; artifacts that cannot safely be removed return a cleanup failure rather than a false cap claim. No abandoned rebuild directory is recursively deleted, and symlink/directory lookalikes are not recovery backups.

If the process dies after moving the old main but before publishing a replacement, a later managed open notices the missing main and retained backup. Under the same recovery lease/circuit it restores missing file-set members without clobbering existing ones, then rebuilds/verifies. This does not establish safety against a live peer handle, stale takeover or power-loss/torn-page behavior. Those remain qualification questions, not a native-only protocol repair.

## Dormant snapshot maintenance

`memory.Maintain(ctx)` sweeps the global store and immediate nonhidden project directories, skipping symlinks, nested directories and `skills`. It takes each document's existing mutation lease and reuses publication's snapshot policy for `MEMORY.md`, `USER.md` and `failures.md`. It does not load, rewrite or reconcile those documents. Failed stores are returned explicitly alongside the successful-store count.

Maintenance has a 30-second cancellation budget. The existing per-kind 32-file/64-MiB policies remain, with seven-day active recovery retention (keeping the newest within the byte budget) and 30-day retired/conflict retention. Expired active snapshots are streamed through a private retired snapshot before removal; a large snapshot is not loaded wholly into memory. Cancellation is checked between files and copy chunks. Synchronous local filesystem calls can still delay cancellation; this is not a remote-filesystem deadline guarantee.

The extension starts this sweep independently of the request-scoped SDK context, retains its outcome, and cancels/joins it on replacement or shutdown before closing the managed database. There is no maintenance timer, native command registration, indexing scheduler or learning orchestration in this checkpoint. The selected backend's `/memory-sync-markdown` remains the deployed repair command.

## Publication and rollback boundaries

Lock order is mutation lease → database-owner admission → recovery lease when reconciliation encounters corruption. Integrity work takes database-owner admission → recovery lease; snapshot maintenance takes only the relevant mutation lease. There is no model request or foreground completion under a SQL transaction.

Each candidate-row insert is a private SQLite commit. The visible database changes at the later main-file rename, separately from each lease check and each WAL/SHM move. Reconciliation linearizes at its scoped SQL commit; it remains separate from the earlier document publication. Restoration has separate copy/link operations, not an atomic file-set transaction. A process death or peer write can occur in any of these gaps. Keep the existing bounded model and concrete stale-owner/open-handle traces unchanged; passing feature checks cannot qualify those failed invariants.

Rollback means stopping/joining native work and selecting the existing backend against the same schema or an explicitly restored disposable backup. No down-migration or destructive schema downgrade is introduced. This implementation does not authorize live backup, selection changes or activation, and a successful Nix build alone is not rollback evidence.
